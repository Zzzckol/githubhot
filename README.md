# githubhot

GitHub 热门项目聚合站。产品形态参考 aihot.news，内容换成 GitHub 项目。

双击 `index.html` 打开。不需要服务器、不需要数据库、不需要装东西。

---

## 怎么更新（最常用的一条）

**双击根目录的 `更新.bat`**，等它跑完，回浏览器按 Ctrl+R。

它做三件事：抓 GitHub 最新数据 → 回填中文文案（走本地库，不花钱）→ 把 `index.html` 里的 `?v=` 版本号改成当天日期（防止浏览器拿旧缓存，这就是"刷新了但日期没变"的常见原因）。

命令行等价写法：

```bash
node pipeline/update.mjs
```

抓取失败不会破坏已有数据，页面还能正常看。

### 为什么刷新没用

这个站是**静态**的——数据是一个 `.js` 文件，页面只负责读它。不跑抓取，文件里就永远是上次那份，刷新一百次也一样。要让「每天自动变」，只有两条路：GitHub Actions（见下），或者在这台机器上做定时任务。

## 页面上有两个版本

默认打开的是**今天自动抓取版**（60 条，每天更新）。日期那行右侧可以切到**手写精选存档**（40 条，2026-10-22 定的，固定不变）；日期下面那排圆角标签是**往回看**，能翻过去每一天。

| 地址 | 版本 | 条数 |
|---|---|---|
| `index.html`（默认） | 今日自动抓取 | 60 |
| `index.html?auto=0` | 手写精选存档 | 40 |
| `index.html#/d/2026-10-23` | 某一天的历史榜单 | 60 |

前两个用 **不同的 query 值**切换（`?auto=0` ↔ `?auto=1`），不是只改 hash。原因：如果两边都指向 `#/`，浏览器认为地址没变，不会重新加载，点了就像没反应——这个坑踩过一次。历史日期只用 hash 就行，因为确实换了地址，不用重载。

**今日自动抓取（默认）**
`pipeline/fetch.mjs` 现场调 GitHub 接口抓的 60 个项目。指标全是真的，和上一次的快照对比算日增，跑一次刷新一次。中文文案来自 `pipeline/zh.json` 本地文案库，目前 90 条，全部手写。

**手写精选存档**
40 个精选项目，数据是 2026-10-22 15:40 的快照，固定不变。当初是拿来定产品形态的，现在留着做对照——想看「人工挑一遍」和「机器筛一遍」的差别，切过去比就知道。

**往回看（历史榜单）**
`pipeline/archive.mjs` 把三样东西拼起来：`boards/` 里那天谁在榜、`history.json` 里那天各项目多少星、`meta.json` 里累积的项目元数据（中文说明、语言、分类）。产出 `assets/data.archive.js`，前端直接渲染，不需要请求接口，所以 `file://` 双击打开也能用。

- 只留最近 **120 天**，更老的仍在 `pipeline/boards/` 里没丢
- 中间断过档（比如休假没跑）会如实标出来：日期下面写「对比 10月23日（中间空了 2 天）」，不假装是昨天
- `meta.json` 只增不减，跑得越久覆盖越全；老项目掉出榜单后照样有中文文案

## 怎么看出每天的变化

GitHub 热门有惯性：一个大项目能在榜上待一个月，所以只问「今天谁热」会觉得每天差不多。这版加了**榜单对比**：

- 每天把「当天这 60 个是谁、什么名次」存一份到 `pipeline/boards/YYYY-MM-DD.json`
- 第二天跑的时候，拿今天的榜和昨天的榜逐条比

于是多了几个信号：

| 标记 | 什么意思 |
|---|---|
| **新上榜**（绿） | 昨天不在这 60 个里 |
| **↑4**（蓝） | 昨天第 5 名，今天第 1 名 |
| **↓2**（红） | 名次下滑两位 |
| **连续 7 天**（灰） | 连续在榜天数，≥3 天才显示，用来认出「钉子户」 |

页面上的四个入口：

1. **标题下那行**：`对比昨天：25 个新上榜，35 个还在榜，17 个名次上升，16 个下滑`，右边「只看新进」点了直接筛
2. **筛选条**里的绿色 chip「今日新进 25」
3. **右侧栏第一块**「今日新进」，按今日涨星排
4. **详情页**：`昨天第 5 名 → 今天第 1 名（↑4）· 连续 2 天在榜`

**注意区分两件事**：`新上榜` 只说明它昨天不在这 60 个里——可能是刚发布，也可能是老项目昨天没挤进来。项目本身新不新，看「上线 N 天」。老项目回榜往往是真信号（比如突然发了大版本）。

榜单存档只增不改，删了哪一天的历史就从哪天断掉，所以别手动清 `pipeline/boards/`。

## 管线怎么跑

```bash
node pipeline/fetch.mjs                                    # 抓取 → assets/data.js
node pipeline/fetch.mjs --out assets/data.auto.js --var GH_DATA_AUTO
node pipeline/fetch.mjs --dry                              # 只打印统计
node pipeline/fetch.mjs --force                            # 忽略当日缓存，强制重抓
node pipeline/test-delta.mjs                               # 测增量算法，不联网
```

`fetch.mjs` 做四件事：

1. **抓取** — 三个搜索查询（近两周新建 / 近四个月站稳 / 今年最热），一次约 300 个候选
2. **算日增** — 和 `pipeline/history.json` 里昨天的快照对比
3. **排序** — 有真实日增的按日增排，没有的按「总星数 ÷ 上线天数」
4. **分类** — 强特征一票定音（10 分）、弱特征累加（1 分）的关键词规则

不需要登录也能跑（搜索额度 10 次/分钟，脚本只调 3 次）。设了 `GITHUB_TOKEN` 额度更宽松。

同一天的抓取结果缓存在 `pipeline/cache/`，重跑不消耗接口额度。

### 为什么要存历史

第一次跑只记一条快照，算不出「今天涨了多少」，页面上显示的是「终生日均」（总星数 ÷ 上线天数）。**第二次跑开始才有真实日增。** 跑得越久，能算的东西越多：7 天增量、连续上榜天数、涨星曲线。

## 补中文文案

抓来的描述是英文的。`enrich.mjs` 负责把它变成中文说明和推荐理由，走**两层**：

**第一层：本地人工文案库 `pipeline/zh.json`**（免费，不需要任何 key）

`{ "仓库id": { "desc": "一句话说明", "why": "为什么值得看" } }`

命中就直接用。这一层永远是首选——手写的判断比模型稳定，也不会为了凑字数说空话。现在的 60 条全在这一层。

**第二层：模型**（只有本地库没命中的新项目才用）

```bash
node pipeline/enrich.mjs --local-only   # 只填本地库，剩下的保留英文（CI 默认就是这一档）
node pipeline/enrich.mjs                # 本地库 + 模型兜底，需要 key
export LLM_API_KEY=sk-xxxx              # PowerShell: $env:LLM_API_KEY="sk-xxxx"
node pipeline/enrich.mjs --only 10      # 只跑前 10 条试水
node pipeline/enrich.mjs --overwrite    # 全部重写（会连本地库的一起覆盖）
```

可选环境变量：`LLM_BASE_URL`（默认 `https://api.deepseek.com/v1`）、`LLM_MODEL`（默认 `deepseek-chat`）。

所以：**不配任何密钥，这个站也是全中文的**。只有日后抓到本地库里没有的新项目，那几条才会回落显示英文，把它们的 id 补进 `zh.json` 就行。

几点设计上的取舍：

- **排序不归模型管。** 排序永远由真实数据决定，模型只写文案。否则「什么值得看」就变成模型的嘴了。
- **提示词里明确要求说人话**，禁用「赋能 / 抓手 / 闭环 / 生态位」这类词，禁止三段式排比，允许泼冷水。
- **禁止编造**：只给模型描述、topics、星数、上线天数、是否官方账号，没给的一律不许写。
- 每条单独缓存，中断了下次不用重写。
- 成本：只有本地库没命中的条目才会调模型，60 条全新大约 8 次调用，DeepSeek 一轮几毛钱。

## 想每天自动跑

两条路，都装。**本地这套管你人在的时候，Actions 管你休假、关机的时候。**

### A. 本机开机自启（已装，2026-10-26）

`schtasks` 被安全策略拦了，所以没走计划任务，走的是「启动文件夹 + 常驻守护」：

```
启动文件夹\githubhot-daily.cmd   →  pythonw pipeline\auto-daily.pyw（无窗口）
pipeline\auto-daily.pyw          每 30 分钟醒一次，发现当天没有 boards/<今天>.json 就跑一次 update.mjs
```

- 日志：`pipeline/out/auto.log`（超过 200 KB 自动砍掉前一半）
- 进程：`pipeline/out/auto.pid`；单实例靠占本地端口 52913，起两个也只会活一个
- 抓取失败（断网、限流）会在 20 分钟后重试，直到当天抓成功
- 想临时停：双击 `关闭日更.bat`
- 想彻底关：删掉启动文件夹里的 `githubhot-daily.cmd`（win+R 输入 `shell:startup` 打开）

**限制**：电脑得开着。关机、休眠、没登录的那段它不跑，开机后只补当天那一次，中间断掉的日期补不回来。

### B. GitHub Actions（休假、出差时的唯一解）

云端每天跑，跟你电脑开不开无关。`daily.yml` 已配好两班：**北京 08:00 主跑，12:00 补救**。12:00 那次会先看当天有没有存档，有就跳过，没有才干活——所以既不会重复抓，也不会因为早上那次失败就整天没有。

推送前要做的：

1. GitHub 上建一个 **public** 空仓库（public 才能免费用 Pages；私有仓库的 Actions 也能跑，但页面托管要钱）
2. 把本机公钥 `~/.ssh/id_ed25519.pub` 加到 GitHub → Settings → SSH and GPG keys
3. 本地加远端并推送：`git remote add origin git@github.com:<你的用户名>/githubhot.git && git push -u origin main`
4. 仓库 Settings → Pages → Source 选 `Deploy from a branch`，分支 `main` / 根目录。地址是 `https://<你的用户名>.github.io/githubhot/`
5. 仓库 Settings → Actions → General → Workflow permissions 选 **Read and write**（不选这步，每天跑完 push 会失败）
6. Actions 页面点一次「Run workflow」手动验证

配 `LLM_API_KEY` 是可选的（Settings → Secrets → Actions）。不配也能全中文，走 `pipeline/zh.json` 本地库；以后抓到库里没收录的新项目，那几条会回落英文，补进 `zh.json` 就行。

**注意**：`github.io` 在国内访问时快时慢，手机上打不开是常态，翻墙才能稳定。要国内稳定访问得自己上服务器或对象存储 + CDN，那就不免费了。

### 这套有个绕不开的坑（已修）

原来 `daily.yml` 有两处会让云端版本看起来「没更新」或者「永远没有名次变化」：

- `git add` 漏了 `pipeline/boards/`，云端每天跑完不提交榜单存档 → 第二天没有「昨天的榜」可比，新上榜、名次升降、连续在榜全部失效
- 没刷新 `index.html` 里的 `?v=` 版本号 → 浏览器一直吃旧的 `data.auto.js` 缓存，数据变了页面也不变

现在提交时一起 add `pipeline/boards` 和 `index.html`，抓完先跑 `pipeline/stamp.mjs` 刷版本号（按北京时间算日期，不会在跨零点时差一天）。

  boards/                   每日榜单存档（谁在榜、第几名），对比和回溯靠它

## 已知问题

- **数据是快照，不是实时。** 本机每天自动跑一次（开机自启），推到 GitHub 后云端每天两次；但页面拿到的是「上一次生成时」的数据，不是此刻的。想看最新的，双击 `更新.bat` 或跑 `node pipeline/update.mjs`。
- **榜单对比要有历史垫底。** 第一次跑没有「上一次」可比，页面上不会出现新上榜标记；跑满两天才准。断一天（没跑更新），那一天的榜位变化就永久缺失——`archive.mjs` 会把它标成「中间空了 N 天」，但补不回来。
- **历史归档依赖 `boards/`。** 哪天没跑，那天就没归档；删了 `pipeline/boards/` 里的文件，对应的历史日也跟着消失。
- **「本周涨星」现在还是空的。** 历史只攒了两天，要 5~9 天前的快照才能算周增量。跑够一周就自动出来。
- **分类准确率约八成**。明显错判的是两类：没写描述的项目（只能落兜底）、以及「AI 助手」这种跨界的。要更准只能让模型判。
- **候选池偏 AI**。三个查询都按星数排序，而 2026 年新建就爆的项目几乎全跟 AI 有关。想让游戏、设计、数据类项目多进来，要加按语言或按 topic 的查询。
- **没有事件聚簇**。同一波热潮下的几个项目现在只能靠分类标签粗略区分。
- **没有涨星曲线**。历史表已经在存了，但前端还没画。

## 数据来源与声明

- 项目、星数、Fork、语言、创建时间：GitHub 官方搜索接口
- 中文说明与推荐理由：全部逐条手写（`pipeline/zh.json` + `assets/data.js`），没有一条是模型批量生成的。模型只负责日后新出现、本地库还没收录的项目
- **文案的可信边界（重要）**：写的时候只有仓库的一句话描述、topics、星数 / 上线天数 / 是否官方账号这几样东西，除了明确写了「试过」的，**项目没有逐个实际运行过**。所以页面上的话分三档——数字（GitHub 接口，可自核）、转述（README 说的，可能滞后于代码）、判断（编辑看法，会错）。发现哪条判断站不住，改 `pipeline/zh.json` 对应那一行、重跑 `enrich.mjs --local-only` 就生效（本地库是权威，会覆盖已有文案）
- 名字 githubhot 是临时名。aihot 在其 README 中明确要求不得使用 AIHOT 的名字与 Logo，本项目仅参考产品思路，未使用其任何视觉资产
